## Blocking finding SR-01 — CLI runbook puts private configuration on process argv

**Observed:** `app/RUNBOOK.md:19-23` tells operators to define `ash()` with `sudo -u ashfall-promo env $(sudo grep -v '^#' /etc/ashfall-promo/app.env | xargs) /usr/bin/node ...`. The same unsafe pattern appears in `app/server/cli.mjs:2`. The documented private file can contain `ASHFALL_SIGNUP_INVITE_CODE` (`app/deploy/app.env.example:19-22`); future variables may be more sensitive. Shell substitution expands assignments into arguments to `sudo`/`env`, rather than relying on systemd's EnvironmentFile, and `xargs` also mangles whitespace/quoting. A local process observer with ordinary process-list access may sample an argument containing the invite code while the command starts; malformed values can cause an operator command to fail. No real secret was inspected or exposed during this review. **Severity: Moderate; confidence: High in the unsafe construction, medium for practical interception on this particular host.** The attack requires a local observer or process telemetry capture and favorable timing, not a remote unauthenticated request.

**Required remediation:** Replace both examples with a narrowly scoped, root-controlled mechanism that reads the env file without placing values in command arguments or shell traces, using systemd `EnvironmentFile=` in a transient service or an equivalent validated environment-loading wrapper with no `eval`, no world-readable temporary file and no secret-echo. Exercise a CLI status/backup/grant command against an isolated env file containing a non-secret sentinel with spaces/special characters, and show that `/proc` command lines and logs contain no assignment value. Rebuild the manifest/tarball and submit the new release ID and SHA-256 for focused re-review. Do not deploy this tarball unchanged.

## Controls observed in app code and negative testing

- Passwords are salted with 16 random bytes and asynchronously scrypt-hashed (`security.mjs:20-42`, configured N=32768 production); password hashes and sessions are stored in SQLite, raw session tokens only as SHA-256 digests. Random new token per login; logout deletes the matching DB row; password change removes other sessions. Node's scrypt guidance supports a random salt of at least 16 bytes: https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback
- `__Host-` session and anonymous CSRF cookies set `Secure`, `HttpOnly`, host-only `Path=/` and SameSite; the public origin must be HTTPS. Origin/Fetch-metadata plus per-session or anonymous double-submit CSRF token checked for every POST (`app.mjs:158-180,615-621`). The app does not infer HTTPS from forwarded headers.
- Server-side ownership and moderator checks guard edit/delete/report/like/lock/suspend; the moderator role is granted from the local CLI, not by first signup or a hardcoded public password. SQL is parameterized (`store.mjs`); HTML templates escape interpolation and user-authored post bodies (`html.mjs`); script CSP is self-only and client `innerHTML` assignments use only constant fragments or clearing.
- Body, field, username and post size limits plus in-memory per-user, per-account and per-address throttles are present. Static assets come from an exact-match map of `dist/public`; the DB/content/build inventories are not served. The privacy notice describes account/post data, cookies, logs, deletion and backup retention; it does not collect email. Logs omit query strings, cookies, IPs and request bodies. The phrase "never ... see the password itself" at `views.mjs:251` is imprecise (the server must briefly receive it to hash it); amend as a non-blocking clarity improvement.

## Deployment-only conditions — NOT tested and NOT approved by this review

- `ops/PREFLIGHT.md:87-95` is a plan, not an active route. Kong is host-networked and the app sees loopback. With `ASHFALL_CLIENT_IP_HEADER` empty (`app.env.example:17`), per-IP limits are **global across all visitors**. With it set, the app accepts any syntactically valid single IP header from a loopback peer (`app.mjs:89-98`); thus the Ashfall-specific Kong route MUST overwrite/remove any client-provided instance authoritatively using its actual socket peer and preserve the canonical Host. Prove from the public ingress that forged `X-Ashfall-Client-IP`/`X-Forwarded-*` do not change throttles, cookie/origin behavior or redirects, while distinct clients do not share limits. Do not set the variable until this proof passes. No global Kong trust setting or client-controlled header may substitute.
- The current preflight cert lacks the Ashfall SAN, and ingress Host/SNI and HTTP challenge guards deny it. Require the preflight's narrow four-host certificate, exact Host/SNI equality, Ashfall-specific HTTP->HTTPS redirect, private `127.0.0.1:3187` backend, Kong request-size control, unchanged sibling routes, backups/restore, public trusted-chain verification and external real signup/post/restart checks before deployment. The DNS record is already exact and unproxied; do not assume Cloudflare WAF protection. No CA/account or live service changes were performed here.
- This is deliberately simple auth for an invited-friends pilot, not an enterprise identity assessment. Rate limits are process-local and reset on restart; social engineering, spam at internet scale, and host compromise are out of scope for this PASS gate.
