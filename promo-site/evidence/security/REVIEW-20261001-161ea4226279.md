## 2. SR-01 (secrets on argv): closed, including the new CLI guard

**Static review.** `RUNBOOK.md` defines `ash()` as a fixed-path `sudo /usr/bin/systemd-run --system … --expand-environment=no --property=EnvironmentFile=/etc/ashfall-promo/app.env … /usr/bin/node …/cli.mjs "$@"` (lines 22–31). The shell passes only the file path. RUNBOOK.md and the packaged `server/cli.mjs` contain no `$(…)`, `xargs`, `eval`, `source`, `env K=V` or secret `--setenv`. The units use `EnvironmentFile=` (lines 13 of both service templates).

`server/cli.mjs` reads configuration only from `process.env`. It never echoes the invite code: the config error for a short invite code does not include the value. The new 71e52 guard is lines 180–194: `isMain()` compares `fs.realpathSync` of `import.meta.url` and of `process.argv[1]`, with a `catch` that returns false. It reads `argv[1]`, which is the script path, and touches neither environment nor argv content. It adds no new channel for a secret to leak through.

**Exercise.** No sudo is available to this review, so the runbook helper's mechanism was reproduced under the systemd user manager. The exact flags were `systemd-run --user --quiet --wait --pipe --collect --expand-environment=no --service-type=exec --property=EnvironmentFile=<isolated 0600 app.env> --property=WorkingDirectory=<release> --property=UMask=0077 --property=NoNewPrivileges=yes --property=MemoryMax=512M --property=MemorySwapMax=64M /usr/bin/node <release>/server/cli.mjs <cmd>`.
- **Environment file.** The isolated env file held a harmless sentinel as `ASHFALL_SIGNUP_INVITE_CODE`. The sentinel contained spaces, `;`, `$HOME`, a backtick, `$(id)`, `|`, `&`, `*`, `?`, braces and quotes.
- **Preload.** A no-output `NODE_OPTIONS=--import` preload did three things: asserted that the value arrived exactly, checked `/proc/self/cmdline`, and held each CLI process for 1.5 s.
- **External sampling.** A sampler read every readable `/proc/*/cmdline` every 50 ms.
- **Commands.** `migrate`, `status`, `backup`, `verify` and `grant-moderator <missing user>`.

Results are in `evidence/qa/20261001-161ea4226279/sr01-cli-results.json`; the sentinel value itself is not recorded.

## 5. Findings

**SR-01 (Moderate, from the 77c53 review): CLOSED in 71e52123197f.** It is also closed in 161ea for argv purposes, but 161ea's CLI does nothing under the release symlink, so 161ea must not be deployed.

**SR-02 (Medium security / High availability). Deployment gate D1 must be met before public exposure; the package needs no change.** `server/app.mjs:581` applies `limit(req.ip, 'requestsPerIp')` (600 per minute, fixed window, `server/security.mjs:154`) to **every** request, including static assets, before the static map at line 583. Behind host-networked Kong with `ASHFALL_CLIENT_IP_HEADER` empty (the template default), `req.ip` is 127.0.0.1 for everyone, so these budgets become **site-wide**.

Measured cold, fully scrolled views of this candidate (`evidence/qa/20261001-161ea4226279/request-cost.json`):

| Page | Requests per cold view | Cold views per minute before the shared budget runs out |
| --- | --- | --- |
| `/` | 17–18 | about 33 |
| `/development` | 32 | about 18 |
| `/gallery` | 40 (was about 17 before this delta) | about 15 |

Past that budget, every visitor gets 429s on CSS, images and pages for the rest of the minute. The review's own harness reproduced this: 83 429s, including CSS and images. The other per-IP limits become global the same way:

- signups: 10 per hour site-wide (`ASHFALL_SIGNUP_PER_IP_HOUR`)
- logins: 20 per 15 minutes site-wide
- POSTs: 120 per minute site-wide

One client can therefore lock everyone out.

The earlier review already required proof "that distinct clients do not share limits" before deployment. This delta roughly doubles the cost of each visit, so the gate is now practical, not theoretical.

- **Required fix (deployment).** The Ashfall Kong route must overwrite (not append) `X-Ashfall-Client-IP` with the socket client IP and strip client-supplied copies. Then prove from the public ingress that a forged `X-Ashfall-Client-IP` or `X-Forwarded-For` does not change throttling, and that two distinct clients have separate budgets. Only then set `ASHFALL_CLIENT_IP_HEADER=x-ashfall-client-ip` and restart.
- **Recommended code change for the next candidate.** In `server/app.mjs`, move the static-asset block (lines 583–599) above `limit(req.ip, 'requestsPerIp')` (line 581), or give statics their own much larger bucket. Even a mis-set or global limiter would then not break images and CSS.

**SR-03 (Low, non-blocking).** `cli.mjs backup` runs `integrity(tmp)` (line 96) on the WAL-mode `.partial` copy, then renames only the main file (line 98). Each backup leaves `community-…sqlite.partial-shm`/`-wal`, and `verify` leaves `-shm`/`-wal`. All are 0600, and the prune pattern (line 101) never removes them, so about 32 KB a day accumulates in `/backup/hdd/ashfall-promo`.
- **Fix:** before the integrity check, set `PRAGMA journal_mode=DELETE` on the backup copy, or remove `${tmp}-shm`/`${tmp}-wal` after `integrity()`. Then prune the `-shm`/`-wal` sidecars alongside each pruned file.

**Carried-over deployment gates, not tested here:**
- **D2: the PREFLIGHT §5–6 ingress and TLS work.** This means:
  - an exact Host/SNI certificate with the Ashfall SAN
  - an HTTP→HTTPS redirect for this host only
  - the private `127.0.0.1:3187` backend
  - a Kong request-size limit of 16 KB or less
  - sibling routes left unchanged
- **D3: on-host checks.** The real `ashfall-promo` system unit and `ash` helper, a restore drill, and an external signup, post and restart check.

None of these were exercised or approved by this review.
