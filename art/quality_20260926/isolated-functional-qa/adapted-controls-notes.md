# Software-adapted controls fallback

`adapted-controls.py` is a separately identified fallback for the private Xvfb llvmpipe player. It has been prepared and syntax checked, **not executed**. The original `unity/tools/controls_check.py` is unchanged. A successful adapted run would not mean the original controls test passed, and would not establish native GPU performance or smooth motion.

Run only through the sibling `run_adapted.py` wrapper after the owner explicitly hands over the private player's input and command stream. The wrapper checks the llvmpipe launch record, scopes the X display/PID/mailbox, verifies focus and 1920×1080 geometry, disables key autorepeat only on the private Xvfb display, and restores it on exit. This staged script does not launch or alter a player.

## Exact changes from the original contract

- Wall-clock input/settlement delays become observed `snapshot.frame` barriers, each bounded at 60 seconds. Command acknowledgments use the shared 60-second client. A camera baseline is refreshed before each independent comparison.
- A drag still uses six pointer increments and the original coordinates/deltas. Pointer placement settles for two frames; the held mouse press settles for two frames before motion, because `GameInput` intentionally ignores look delta on the press frame. Each increment gets one fresh frame; release gets two. Every pressed mouse/key is released in `finally`.
- Wheel events get two fresh frames each. The two 30-event saturation sequences may stop after reaching the same bound and delivering one further event; the original endpoint assertions remain unchanged. Other event counts remain unchanged.
- Independently of software timing, the original hard-coded HUD point `(840, 960)` is stale for the current layout: the observed slot 1 bounds are `(629, 988, 64, 64)`. The fallback requests a fresh `uiSnapshot`, selects visible/enabled `slot1`, converts its center from panel units using the measured HUD root width, and uses that target for drag, wheel and click. The actual layout and target are preserved in evidence. The camera-blocking and Flask notice assertions are unchanged.
- Forward movement holds W until the original distance condition exceeds one metre, bounded at 60 seconds, then releases and settles for two frames. The original distance and eye alignment tolerances remain unchanged; the original 0.4-second timing is not tested.
- Left-drag yaw/pitch thresholds, unheld/right-drag/HUD camera tolerances, Flask notice, first-person visibility/eye height, zoom limits, modal states/input blocking, and all 16 landmark/yaw clearance assertions are unchanged. Capture names and all result paths are explicitly prefixed/adapted so original evidence is preserved.
- The held Space test records every physics update using the existing read-only development motion recorder. Space remains physically held through the whole trace, including its landing tail. It asserts exactly one accepted jump, the original `0.95 < peak < 1.5` metre bounds, final grounded state, original final-height tolerance `< 0.05` metre, and that **all fixed samples later than one simulated second after takeoff are grounded**. An empty late-sample set fails. This is a separately labeled fixed-step physics check; no rendered peak or visual timing claim is made.
- A separate one-frame Space pulse records fixed-step jump/landing evidence with the original short-jump peak bounds `0.9 < peak < 1.5`, exactly one accepted jump and the same landing checks. It does **not** exercise an 8 ms tap or send an airborne second press. Those two original timing-sensitive cases are explicitly listed as **not tested**, because a delayed second press could arrive after landing at this renderer's cadence. No no-double-jump claim is made.

Motion JSON is copied immediately to a unique report file before another recording can replace the native `motion.json`. Reports refuse to overwrite earlier adapted results. Interrupted recordings are stopped and copied when possible, and cleanup failures are recorded. The shared wrapper records source hashes, elapsed time, rendering profile, input isolation and autorepeat restoration.

The new hardware-backed Zink path should attempt the original checks with their original timing first. This fallback remains staged only unless explicitly selected; Zink is a separate renderer profile and still cannot qualify the desktop OpenGL target by implication.
